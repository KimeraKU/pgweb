# 登录注册流程 PRD V2

## 1. 文档目标
- 说明当前站点认证弹窗的完整流程与分流规则。
- 明确“邮箱先输入，再判断账号状态”的新方案。
- 为后续接入真实账号系统、邮箱验证与 OAuth 提供清晰产品依据。
- 配套最新页面截图，便于设计、前端、后端同步。

## 2. 适用范围
- 页面入口：首页导航栏 `登录` 按钮
- 形态：站内弹窗，不跳独立路由
- 适用用户：未登录用户

## 3. 方案概述
本版流程采用“先选方式，再录邮箱，再按账号状态分流”的结构：

1. 用户点击 `登录`
2. 先看到登录方式选择弹窗
3. 若选择邮箱，则先只输入邮箱
4. 系统根据邮箱状态分三路：
   - 已注册且可登录：进入密码登录页
   - 已注册但未完成邮箱验证：进入邮箱验证提示页
   - 未注册：进入注册补全页

这个方案比“先输入邮箱和密码，再判断新老用户”更符合主流产品逻辑，也能减少无效输入。

## 4. 流程总览

### 4.1 顶层主路径
- `登录方式选择`
- `邮箱输入`
- `已注册用户 -> 密码登录`
- `未激活用户 -> 邮箱验证提示`
- `新用户 -> 注册补全`
- `忘记密码`

### 4.2 状态流转
- `methods -> email-entry`
  - 点击 `使用邮箱继续`
- `email-entry -> email-login`
  - 邮箱存在且已注册
- `email-entry -> activation-required`
  - 邮箱存在但未完成验证
- `email-entry -> email-register`
  - 邮箱不存在，需要创建账号
- `email-login -> reset-password`
  - 点击 `忘记?`
- `email-login -> email-entry`
  - 点击 `更换邮箱`
- `email-register -> activation-required`
  - 注册提交成功
- `activation-required -> email-entry`
  - 点击 `更换邮箱`
- `activation-required -> email-login`
  - 点击 `返回登录`
- `reset-password -> email-login`
  - 点击 `返回`

## 7. 详细规则

### 7.1 邮箱状态判断规则
系统需判断邮箱属于以下哪一种状态：

1. `existing_active`
   - 已注册
   - 已完成邮箱验证
   - 可直接进入密码登录

2. `existing_pending_activation`
   - 已注册
   - 未完成邮箱验证
   - 不允许登录
   - 进入邮箱验证提示页

3. `new_user`
   - 邮箱不存在
   - 进入注册补全页

### 7.2 字段规则

#### 邮箱
- 必填
- 必须符合标准邮箱格式

#### 登录密码
- 必填

#### 注册密码
- 必填
- 当前前端规则：不少于 8 位
- 页面提示文案当前为：`密码应为6-20个字符`
- 该规则需要后续和服务端统一

#### 确认密码
- 必填
- 必须与设置密码一致

## 8. 交互原则
- 不要求用户在未知账号状态下先输入密码
- 新老用户分流应尽量自动完成
- 邮箱验证是注册后的必要步骤，不应默认绕过
- 所有阻断状态都应给出明确下一步操作
- 弹窗尺寸固定，不随状态变化而跳动

## 9. 当前实现说明
- Google / Apple 登录入口为前端预留入口
- 邮箱状态判断当前使用 mock 数据：
  - 已注册邮箱集合
  - 未激活邮箱集合
- 邮箱验证、登录成功、注册成功、重设密码均为前端原型行为
- 实际生产环境需由服务端接口决定账号状态与认证结果

   - 判断 `existing_active / existing_pending_activation / new_user`
2. 接入 Google OAuth

5. 接入邮箱注册接口

## 11. 验收标准
1. 点击 `登录` 后，先展示登录方式选择页
2. 点击 `使用邮箱继续` 后，先进入“邮箱输入页”
3. 已注册邮箱提交后进入“密码登录页”
4. 未激活邮箱提交后进入“邮箱验证提示页”
5. 新邮箱提交后进入“注册补全页”
6. 注册成功后进入“邮箱验证提示页”
7. 忘记密码入口可从“密码登录页”进入
8. 各页支持正确返回，不出现死循环或错误跳转
9. 弹窗尺寸在不同状态下保持一致
10. 每个页面状态都有对应截图可供对照
