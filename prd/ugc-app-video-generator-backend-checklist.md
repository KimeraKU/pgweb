# UGC App Video Generator 后端对齐清单

## 1. 目的
用于和后端快速对齐：把当前 Demo 接入公司现有的登录体系、API 网关、AI token/积分计费、任务存储与媒体存储能力，支持上线版本。

## 2. 当前 Demo 现状（便于后端理解改造范围）
- 前端页面：`/ugc-video-generator`
- 当前主要走 Next.js API Route 作为代理层（`/api/*`）
- 生图/生视频任务历史目前主要在前端 IndexedDB 本地存储
- 尚未接入统一登录态、用户鉴权、统一积分扣费、后端任务持久化
- 存在多上游供应商调用（上传、生图、视频、审核、prompt 优化）

## 3. 需要后端支持的能力总览
- 登录态接入：统一用户身份、租户、权限
- 统一 BFF/API：对前端暴露稳定接口，屏蔽多上游细节
- AI 计费：token 统计、积分冻结/扣减/退款、账单流水
- 任务中心：图片 run、视频 task 的持久化与状态机
- 存储：图片/视频 URL 持久化、过期策略、可回放
- 回调与轮询：任务结果回传、失败重试、幂等保障

## 4. 和后端逐项核对清单

### 4.1 登录与鉴权
- 登录态来源：Cookie Session / JWT / SSO（明确一种）
- 前端调用 BFF 是否需要携带 `Authorization`，刷新机制如何做
- 用户与租户字段：`user_id / tenant_id / app_id` 的映射规则
- 鉴权粒度：谁可以创建任务、谁可以查看/重试历史任务
- 跨端一致性：Web 与 App 是否共享同一用户 ID

### 4.2 API 接入与网关
- 是否由后端统一托管所有上游（上传、审核、生图、生视频、LLM）
- 网关超时、重试策略、熔断策略、限流策略
- 错误码规范：业务码 + HTTP 码，前端可稳定识别
- 幂等键策略：防止重复点按钮造成重复扣费/重复建任务
- 回调验签：上游回调是否验证签名、如何防重放

### 4.3 AI Token 消耗与积分体系（重点）
- 计费粒度：
  - prompt 优化（图/视频）是否单独计费
  - 图片生成是否按候选张数计费（1-8）
  - 视频生成是否按任务计费
- 扣费时机：
  - 创建任务前预扣（冻结）
  - 成功后结算，失败是否全退/部分退
- 部分成功场景：
  - 8 张候选图只成功 3 张，怎么结算
- Regenerate 场景：
  - 图片/视频重生成是否视为新计费事件
- 账务流水：
  - 必须可追溯到 `run_id/task_id/request_id`
  - 用户可查消费记录（至少后台可查）
- token 统计口径：
  - LLM 输入/输出 token 统计来源
  - 上游模型无 token 返回时的折算规则

### 4.4 任务模型与状态机
- 图片任务模型：
  - `image_run`（一组候选）与 `candidate`（单张）是否拆表
- 视频任务模型：
  - `video_task` 状态：`video_prompting/reviewing/generating/submitted/completed/failed`
- 状态流转是否允许回退，哪些状态可重试
- 任务排序与分页：按创建时间倒序，接口是否支持 cursor
- 历史保留策略：保留天数、归档策略

### 4.5 存储与媒体管理
- 统一对象存储方案（OSS/S3/COS）与访问域名
- URL 有效期：长期公开 / 短链签名（到期策略）
- 原图、中间图、视频封面、视频文件分别如何存储
- 去重策略：相同文件是否秒传/复用
- 清理策略：失败任务和临时文件自动清理时机

### 4.6 回调、轮询与一致性
- 是否以后端回调为主，前端只查后端状态
- 回调失败重试机制（次数、间隔、死信处理）
- 前端轮询间隔与上限是否由后端下发配置
- 回调先到、前端后查的并发一致性处理

### 4.7 可观测性与排障
- 统一 trace id：前端请求 -> BFF -> 上游全链路打通
- 日志关键字段：`user_id/run_id/task_id/provider/request_id`
- 指标：成功率、P95 延迟、失败原因 TopN、重试率、退款率
- 告警：上游错误率突增、回调堆积、扣费异常

### 4.8 风控与合规
- 图片审核失败时的提示文案与重试策略
- 审计要求：操作日志、扣费日志、任务操作来源（IP/UA）
- 密钥管理：禁止前端暴露供应商 key，统一后端托管

## 5. 建议后端统一接口（可作为讨论起点）
- `POST /v1/ugc/image-runs`
- `POST /v1/ugc/image-runs/{runId}/regenerate`
- `GET /v1/ugc/image-runs?cursor=...`
- `POST /v1/ugc/video-tasks`
- `POST /v1/ugc/video-tasks/{taskId}/regenerate`
- `GET /v1/ugc/video-tasks?cursor=...`
- `GET /v1/ugc/tasks/{id}`（统一详情）
- `GET /v1/ugc/billing/records?cursor=...`
- `POST /v1/ugc/callback/{provider}`（内部回调入口）

## 6. 联调前必须拿到的后端产物
- 接口文档（OpenAPI/Swagger）
- 鉴权接入说明（登录态透传方式）
- 错误码字典（可前端直接映射）
- 积分规则文档（扣费/退费）
- 回调字段样例（成功/失败各一份）
- 环境信息（dev/staging/prod 域名、白名单、限流）

## 7. 会议可直接使用的问题清单（建议逐条过）
1. 这个项目最终是“前端直连现有 `/api/*`”还是“统一迁移到后端 BFF”？
2. 登录态打通后，`user_id/tenant_id` 以谁为准，是否允许匿名试用？
3. 图片生成和视频生成分别怎么计费？失败退款规则是什么？
4. Prompt 优化（LLM）是否计费？token 如何统计与落库？
5. Regenerate 是否按新任务计费？有无防刷限制？
6. 任务历史是否后端持久化？保留多久？是否支持跨设备同步？
7. 媒体 URL 是否长期有效？如果失效，前端如何刷新可用链接？
8. 回调与轮询谁是主链路？如何保证最终一致？
9. 幂等如何做（重复点击、网络重试、回调重复）？
10. 上线前需要哪些压测、风控、审计、监控阈值？

## 8. 建议推进顺序
- 第 1 阶段：登录鉴权 + 后端任务持久化（不改 UI）
- 第 2 阶段：积分扣费与账单流水接入
- 第 3 阶段：回调主链路与可观测完善
- 第 4 阶段：历史迁移与数据治理（清理/归档）

## 9. 你可以这样分工
- 你（产品/前端）：确认业务规则、异常提示、交互验收
- 后端：接口与状态机、计费与幂等、回调与存储
- 算法/平台：上游供应商 SLA、token 统计、审核策略
- QA：核心链路用例（成功/失败/部分成功/重复点击/断网恢复）
